# Confidence Calibration: Measuring Threshold Reliability Across Document Quality

This harness measures whether Unsiloed's confidence scores and thresholds remain reliable as document quality degrades — answering three questions from Unsiloed's own "Confidence Score Reliability: The Missing Metric" blog:

1. **Which score to trust?** `grounding_score`, `extraction_score`, or `min(grounding, extraction)` — and do they predict correctness equally?
2. **Are scores well-calibrated?** Does a 0.9 confidence actually mean 90% accuracy, or does calibration drift as documents get harder?
3. **Do fixed thresholds survive document degradation?** The cookbook ships thresholds of 0.85 and 0.97 — do they hold on clean PDFs *and* on photographed documents?

## What you'll learn

- How to measure confidence score calibration reproducibly, without hand-labeling documents
- Why `grounding_score` and `extraction_score` are equally predictive for the "should I trust this?" decision
- How confidence scores become unreliable as documents degrade from clean PDFs → photographed pages
- Why a single global threshold (like 0.85) cannot work across document types
- Why the field *type* matters as much as the document: money and ID fields fail long before free text does

## Key Finding

**The same confidence threshold that works perfectly on clean PDFs becomes dangerously unsafe on poor-quality documents.** Using threshold 0.85:

- **Clean PDF (T0)**: 0% error, auto-accepting 98% of fields (288 accepted) ✓
- **Photographed (T3)**: 43% error, auto-accepting 10% of fields (30 accepted) ✗✗

That 43% is 13 wrong out of 30 accepted, so its 95% interval runs from 27% to 61%. The exact figure is soft; the conclusion is not, since even the lower bound is 27x the 1% target that Unsiloed's own blog sets as the bar.

**And the damage is not spread evenly.** On a photographed document, money fields are read correctly 19% of the time and IDs 35%, while free text holds at 84%. The fields worth extracting an invoice *for* are the ones that break first — a misread word is still recognisable, a misread digit is silently a different number.

**0.97 does not fix this.** It reports 0% error on degraded documents, but from 4 accepted fields out of 294; the interval on 0-of-4 reaches 49%. It is not a safer threshold, it is a threshold that stops answering — 1.4% coverage against 89% on a clean PDF.

Every rate in this recipe carries a 95% interval, and anything resting on fewer than 30 observations is marked as unreliable rather than hidden. One consequence stated plainly: **no tier here demonstrates sub-1% error at 95% confidence**, so the blog's second question does not get the tidy number it asks for.

## What's committed vs generated

- **`documents/*.pdf` and `*.truth.json`** (12 documents, 87KB) are committed. They are small and deterministic — `corpus/generate.py` reproduces them byte-for-byte from a fixed seed — so there is no reason to make a reviewer run anything just to see the corpus.
- **`documents/cord/`** (95 downloaded receipts, ~15MB) and **`documents/degraded/`** (derived tiers) are not committed, and are regenerated by `corpus/cord.py` and `corpus/degrade.py`. `samples/` carries a few committed examples instead:
  - `samples/degradation_ladder.png` — one invoice through all four tiers, side by side. The glare in T3 visibly wipes out the unit-price column, which is exactly the kind of damage this harness is built to catch.
  - `samples/cord/` — three real receipts from the CORD test split with their published ground truth (CC-BY-4.0, NAVER CLOVA AI Research), including the hand-shadow case referenced above.
- **`results/extractions/`** (140 cached API responses) is not committed; `results/figures/` and `results/*.csv` are, so the findings are visible without spending API quota.

## Quick start

```bash
# From the repo root
cp .env.example .env
# Edit .env and set UNSILOED_API_KEY

pip install -e .

cd confidence-calibration

# Generate the corpus (one-time)
python -m corpus.generate        # 12 synthetic documents with exact ground truth
python -m corpus.degrade         # Four degradation tiers (clean → photographed)
python -m corpus.cord            # Download 95 real CORD receipts (CC-BY-4.0)
                                 # 92 of the 95 extracted cleanly; see note below

# Extract documents (one-time, results cached)
python -m calibration.run

# Analyse (re-runnable, zero API calls)
python -m calibration.analyse

# Open the figures in results/figures/
```

Run times: corpus generation ~5s, degradation ~10s, CORD download ~3min, extractions ~5min, analysis ~30s.

## How it works

### The corpus

**Generated**: 12 synthetic documents (5 invoices, 4 statements, 3 ID cards) with exact ground truth by construction. No OCR, no labeling errors.

**Real**: 95 CORD receipts downloaded (CC-BY-4.0, published by NAVER CLOVA researchers) for external validity. 92 of them extracted successfully and are scored here; three (`receipt_048` through `receipt_050`) failed extraction API-side and were never retried. `calibration/run.py` reports failures at the end of a run and is resumable, so re-running retries only those. The reported counts are 92 because that is what was actually measured.

### The degradation ladder

Same documents, four quality tiers:

| Tier | What it is | Simulates |
|------|-----------|-----------|
| T0 | Original digital PDF | downloaded from a portal |
| T1 | Rasterised 150dpi, no text layer | printed and scanned |
| T2 | Plus 1.5° skew, sensor noise, blur | a tired office scanner |
| T3 | Plus perspective tilt, glare, shadows, JPEG q40 | photographed on a phone |

### The analysis

1. **Score discrimination**: Do grounding, extraction, or min(grounding, extraction) predict correctness better? Answer: they're equivalent (~0.86 separation, intervals overlapping).

2. **Reliability diagram**: As document quality drops, do scores become miscalibrated? Answer: yes, and in opposite directions. On T0/T1 the score barely varies at all — 288 of 294 clean-document fields sit in one 0.9-1.0 bucket, so there is no curve to draw. T2 is *under*confident (signed error -0.26) and T3 is *over*confident (+0.07). Note that ECE, which discards the sign, therefore ranks T2 as worse than T3 even though T3 is the tier that ships wrong values as correct.

3. **Threshold sweep**: For each confidence threshold, what fraction auto-accepts and what's their error rate? Answer: T0 accepts 99% at 0.5 with 0% error; T3 accepts 74% at 0.5 with 38.5% error, and never reaches sub-1% error at any threshold tested.

4. **Fixed thresholds**: Do the shipped thresholds (0.85, 0.97) work across all tiers? Answer: 0.85 breaks on T3 (43% error). 0.97 *cannot be shown to survive* — it reports 0% error on T2 and T3, but from only 4 accepted fields out of 294, and the Wilson interval on 0-of-4 runs to 49%. What it demonstrably does is stop answering: 1.4% coverage, against 89% on a clean PDF.

5. **Accuracy by field type**: Does degradation hit all fields equally? Answer: no, and the ordering is inconvenient. On a phone photo, money fields are read correctly 19% of the time and IDs 35%, while free text holds at 84% and currency codes never fail. Redundancy explains it — a misread word is still recognisable, a misread digit is silently a different number. The fields worth extracting an invoice *for* are the ones that break first, and a single averaged accuracy (52% on T3) hides both ends.

## Outputs

All cached in `results/`:

- **`figures/`**: Five PNG charts (discrimination, reliability, threshold sweep, fixed thresholds, accuracy by field type)
- **`scored_fields.csv`**: Every extracted field vs ground truth (2,312 rows)
- **`score_discrimination.csv`**: Which score predicts correctness
- **`calibration_error.csv`**: Expected calibration error per tier, plus `signed_error` and `direction` — ECE takes an absolute value, so the sign is what tells you whether a tier is over- or underconfident
- **`threshold_sweep.csv`**: Coverage and error per threshold per tier
- **`sub_1pct_thresholds.csv`**: Minimum threshold to hit <1% error per tier
- **`fixed_thresholds.csv`**: Error when using 0.85 and 0.97 across tiers, with Wilson intervals and the count actually accepted (`n_accepted`) — a 0% built from 4 fields and one built from 288 are not the same claim
- **`field_type_accuracy.csv`**: Accuracy per field type per tier, with intervals — money and IDs collapse on photographed documents while text survives

## Testing

`calibration/compare.py` decides what counts as "correct" for every field in the corpus, so
it is the actual epistemic foundation of every number in this recipe — a bug here silently
changes headline findings rather than crashing loudly. `calibration/test_compare.py` covers
the parsing and comparison rules directly, including the case that shipped broken in an
earlier version of this PR: `_strip_money` treated every `.` as a decimal point, so "15.000"
(an Indonesian thousands grouping) and "15,000" (the same value, comma-grouped) parsed to
different floats and scored as a mismatch. Stdlib `unittest`, no extra dependency.

```bash
cd confidence-calibration
python -m unittest calibration.test_compare -v
```

## Notes

- **Synthetic documents are realistic but controlled.** Exact ground truth and varied degradation are impossible with real documents. Validity depends on T0 being readable and T3 being genuinely hard (both visually verified).
- **CORD receipts are real but Indonesian.** Thermal paper, hand-written fields, shadows. Scores may not generalise to Western business documents; intent is external validity check.
- **Thresholds are specific to this corpus.** A company's documents may need different numbers. The *methodology* is the reusable part.
- **Scores drift between runs.** Unsiloed's models improve in production. Numbers are indicative; the *shape of findings* (thresholds don't travel) is durable. Results here are as of **2026-09-13**, against whatever `/v2/extract` served that day. This recipe doesn't decide its own re-run cadence — that's a maintainer call (quarterly re-run, a pinned "results as of" note, or accept it drifts) — it just makes sure the date is on record instead of the numbers quietly going stale unlabeled.
- **Some cells are thin.** At 0.85 the T3 accepted set is 30 fields and at 0.97 it is 4. Figures mark anything under 30 as unreliable (dotted lines, wide intervals) rather than hiding it. Treat the direction of these findings as solid and the second decimal place as noise.
